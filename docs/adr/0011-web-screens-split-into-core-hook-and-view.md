# Web screens split into core, hook and view

A web screen whose branches a test should cover is split into three layers. The **core** is pure TypeScript in `shared/` or a `web/src/*.ts` module: decisions, validation, formatting, and the name and args of each named mutation (ADR 0007). The **hook** is one per screen (`useMenuScreen()`), or one per part (below), and calls `useQuery`, `useMutation`, `useIntent` and `useQueryClient`, passing the core's results through. The **view** takes props and renders JSX, with no fetching. The exported screen is `const s = useMenuScreen(); return <MenuView {...s} />`. We split this way so each layer gets the cheapest test that fits it: the core gets unit tests in Node, as `shared/` does today. The view gets jsdom tests that pass plain props, so it needs no faked API. The hook gets jsdom tests against a mocked `api.ts`, and the e2e covers the whole screen. Decided in the grilling session of 28 Oct 2026, from the estimate in [component-tests.md](../research/component-tests.md).

**Amended 28 Oct 2026 (#172).** As first decided, hooks got no test. The owner then decided to test them, so the splits pass SonarCloud's 80% gate on new code, and the Menu screen's split showed that nested parts need a hook each. This ADR now says both. The rerun in [component-tests.md](../research/component-tests.md#rerun-after-the-splits) records why, and drops the faked-API option below.

**Amended 29 Oct 2026 (#190).** The app shell and sign-in talk to Supabase auth directly, not through `api.ts`, so their hook and wired tests also fake `./supabase.ts`, through `vi.mock` with a factory like the API module's. These are the only two of the app's own modules a test may fake.

## Consequences

- **Decisions move out, state stays.** Every component moves any branch or calculation a test should catch into the core. A `useState` that only holds what the cook typed, or a value set once when a form opens, stays in the component. There are no reducers: one would mostly re-describe its fields.
- **Only screens with branches get the split.** A screen with nothing to test stays one component. `StepEditor` goes first, then `MenuScreen`. The Gantt's logic goes into the Plan preview interface ([architecture review](../architecture/2026-10-26-deepening-opportunities.md), candidate 3) and its drags stay in e2e, because jsdom has no pointer capture.
- **The hook stays thin.** If a hook grows a branch, the branch moves into the core. The typed-text and set-once state above may live in the hook or the component, and a hook calls `useQueryClient` to invalidate.
- **One hook per part** when nested parts each need their own mutation. The Menu screen has one each for the Menu list, New Menu, the Menu, a Course, a Dish's scale and the Service form. A parent view takes each nested part as a `render…` slot prop (`renderCourse`, `renderDishScale`), which the wired component fills with the part's hook and view.
- **Hook and wired tests** render the hook through `renderQueryHook()`, or the hook plus view through `renderWired()`, both in `web/test/render-view.tsx`, inside a fresh, real QueryClient with `retry: false`. Only `./api.ts` is faked, and `./supabase.ts` for the app shell and sign-in (amended above), each through `vi.mock` with a factory. They check what callers see: the values the hook returns, each mutation's name and args, and which queries are invalidated (`isInvalidated`, or a refetch when the query is live).
- **View tests** are `*.test.tsx` files run under jsdom through a vitest `projects` entry, with the hook and wired tests, while the `.ts` tests stay in Node. They find elements by role and visible text, check what callbacks are called with, and use no snapshots. Props for loading, error and pending states can be written by hand. Any prop that holds a computed value comes from ADR 0004's walkthrough or a core function run on it.
- **The Playwright e2e stays the only test in a real browser** and the only test that crosses the network.

## Considered Options

- **Keep the logic in components and test it through the DOM** (Testing Library, with the API faked at `fetch`). It needs no refactor, and the tests survive internal rewrites. It was rejected for three reasons. The faked API is a second copy of the server that can drift from the real one. Hand-written fake responses go against "expected values come from a real run". And covering each pair of cook-set inputs through clicks and typing costs more than a unit test does. The hook tests fake the API too, but one layer up, at `api.ts`, with the QueryClient and hooks running for real. That keeps two of the costs at a smaller size: the fake responses are hand-written, and `api.ts`'s return types catch a change in shape but not in behaviour. It adds no HTTP-level copy of each response. The rerun in [component-tests.md](../research/component-tests.md) dropped this option: faking at `fetch` would add only `api.ts`'s own code, which every e2e test runs against the real server.
- **Extract decisions only, without hook and view.** This is the minimum every component meets anyway. On its own it leaves the states a screen shows (loading, error, empty, pending) to the e2e.
- **Split every component.** Presentational and container components applied everywhere, which its own author later stopped recommending once hooks existed. It adds hooks that only wrap `useQuery` and props passed down for nothing.
