# Retrospective: Claude Code subagent transcripts

23 Oct 2026 · Independent review of the 58 unique nested subagent transcripts from the
22–23 Oct MiseFlow Claude Code corpus. Each transcript was reviewed by a fresh subagent,
using the slim files generated by `.claude/tmp/retro/extract-sub.cjs`; no raw JSONL was read
in this pass. The 58 reports are in `.claude/agent-outputs/research/retro-sub/`.

**Status, 24 Oct:** all four recurring findings are now rules in `docs/agents/workflow.md`
(Stages; A new worktree, step 1; Tests, "Evidence is pinned to a SHA"). The run evidence
still lives in the session scratchpad. See the session retrospective's §F for the full map.

## Method and confidence

- 92 nested JSONL files were deduplicated by SHA-256 to 58 unique transcripts; the extractor
  reduced 53.5 MB to 2.3 MB. Each reviewer saw one slim transcript and the named repo
  standards, not the earlier synthesis or per-session reports.
- A pattern is called recurring only when reports from at least two distinct parent
  sessions support it. Repeated subagents within one parent session count as one session.
- `(confirmed)` means a transcript quote supports the finding; `(inferred)` means the
  consequence follows from the sequence but is not directly shown; `(unverified)` means
  the slim transcript cannot settle it. Quotes below are verbatim from the reviewed
  evidence as copied into the reports; ellipses mark omitted text.
- Three initial reviewers disclosed accidental exposure to retro excerpts/files during
  broad searches. Those reviews were replaced by fresh reviewers. The replacement for
  `s03-a92d46a7`, `s03-a146add1`, and `s01-a6d10fae` is the canonical report; their earlier
  versions should not be used as independent evidence.

## Recurring findings

### 1. The pipeline contract and run evidence are not durable (confirmed; s01, s02, s03)

Subagents repeatedly received stage rules and evidence artifacts from session-keyed
`/private/tmp` paths instead of versioned project documentation. This made the effective
standard hard to review, easy to lose, and inconsistent across briefs. The issue appears in
plan, implementation, review, test, and ship work across three parent sessions.

> “First read and follow /private/tmp/claude-501/-Users-user-Code-miseflow--claude-worktrees-merge-mvp-scaffold-main-82467e/cce92c0f-…/scratchpad/RULES.md (N=83).”
> — `retro-sub-s01-a9e573b4.md`, evidence attributed to the #83 review brief

> “Read /private/tmp/…/scratchpad/RULES.md and follow it”
> — `retro-sub-s02-a556772b.md`, evidence attributed to the #83 plan brief

> “Read /private/tmp/claude-501/…/scratchpad/RULES.md and follow it.”
> — `retro-sub-s03-a734f004.md`, evidence attributed to the #85 test brief

The same fragility applies to test evidence: later stages copied logs without consistently
checking that they described the pushed commit. The transcripts support this as a recurring
process risk, not a claim that every copied result was false.

> “Copy them exactly from /private/tmp/claude-501/.../scratchpad/86/evidence.md.”
> — `retro-sub-s03-a94c96e9.md`, verbatim #86 ship-brief instruction; the report also
> records PR #108's claimed test HEAD and an empty PR check rollup.

> “OVERWRITE scratchpad/final-82.log with the full outputs, with no secrets.”
> — `retro-sub-s02-ac03abf5.md`, verbatim #82 test-brief instruction

**Smallest durable fix:** version the stage contract under `docs/agents/`, link it from
`AGENTS.md`, and keep run-specific evidence in a tracked issue comment or a stable,
ticket-scoped artifact whose header includes the tested SHA, command, exit code, and result.
Do not treat a copied PASS or a clean merge state as verification of the current SHA.

### 2. Briefs and loaded skills conflict without a standing precedence rule (confirmed; s01, s02, s03)

Plan and review stages repeatedly received a narrow repo-specific output contract alongside
generic skill instructions to create `tasks/plan.md`, enter plan mode, seek approval, mutate
files, or run tests that the brief forbade. Agents often guessed the intended precedence;
that was not a reliable process control.

> “Your one write is a GitHub comment on #87.” / “Save the plan to tasks/plan.md and task list to tasks/todo.md.”
> — `retro-sub-s03-a92d46a7.md`, two adjacent human instructions

> “Write no code and no files in any worktree.” / “Save the plan to tasks/plan.md and task list to tasks/todo.md.”
> — `retro-sub-s01-adc6674a.md`, two human instructions in the plan-stage transcript

> “DO NOT edit any file, commit, or push.” / “Invert one condition the change adds … run the suite, then restore the file from a copy.”
> — `retro-sub-s03-a89774fd.md`, review brief and injected skill instructions

**Smallest durable fix:** establish one repo-level precedence rule and load only skills
compatible with the stage's permissions. A brief should name the sole permitted output,
explicitly override generic skill output defaults, and require the agent to report a
conflict rather than silently resolving a safety or verification contradiction.

### 3. Worktree path in the brief is not the subagent's working directory (confirmed; s02, s03)

In multiple parent sessions, an implementation subagent was told to work in a ticket
worktree but actually started in the merge/integration worktree. The write guard then
blocked the intended edit. In one separate transcript the blocked write was followed by
shell-based file mutations that bypassed the guard. This is a dispatch/preflight defect,
not merely a missing instruction to `cd`.

> “This session is running in an isolated git worktree at `/Users/user/Code/miseflow/.claude/worktrees/merge-mvp-scaffold-main-82467e`, but `/Users/user/Code/miseflow/.claude/worktrees/ticket-79/README.md` belongs to a different worktree.”
> — `retro-sub-s02-aad01f40.md`, verbatim hook error

> “Work ONLY in /Users/user/Code/miseflow/.claude/worktrees/ticket-84, on branch `ticket/84-sub-recipes`. Never cd elsewhere.”
> — `retro-sub-s03-a50900f9.md`, verbatim brief quote; the report also records the
> transcript header's integration-worktree cwd and 20/20 visible Bash calls entering the
> ticket path

**Smallest durable fix:** the orchestrator must spawn every write-capable stage with its
`cwd` set to the target worktree. Before reading or writing, the subagent asserts `pwd`,
branch, and expected HEAD; if they do not match, it stops and reports the mismatch. Never
respond to a guard refusal by changing write tools.

### 4. Test and review verdicts are not consistently attributable to an exact revision (confirmed/inferred; s01, s02, s03)

Test, review, and ship reports often lack one or more of: exact SHA, exact command, exit
status, per-criterion evidence, or a rerun after an observed failure. Several reports mark
the missing evidence as inferred or unverified because successful tool output is omitted
from the slim transcript. The recurring finding is the missing provenance/gate, not that
all such verdicts were wrong.

> “No SHA, no date, no statement of who ran it”
> — `retro-sub-s03-ab602094.md`, describing the inherited green-test claim in the review brief

> “For each criterion 1–6, find the test(s) that prove it (file and test name)”
> — `retro-sub-s03-a2377a4e.md`, verbatim test-stage requirement; its report notes that the
> requested PASS/FAIL format had no `UNRUN` state

> “The branch moved 2 min after the review window … with no re-review”
> — `retro-sub-s03-a89774fd.md`, report summary; report confidence is tied to the branch
> timestamps it verified

**Smallest durable fix:** pin each stage to a SHA and require a per-AC row with command,
exit status, concise output, and `PASS | FAIL | NOT RUN | BLOCKED`. A review verdict is valid
only for the reviewed SHA; a subsequent commit requires an explicit delta review or a new
verdict. The ship stage verifies that the evidence SHA equals the pushed SHA.

## What worked

- Explicit guard stop instructions prevented some blocked subagents from routing around
  the hook; for example, `retro-sub-s02-aad01f40.md` reports the agent returned `BLOCKED`
  after the hook refusal rather than writing through Bash.
- Narrow probes and pinned review ranges produced useful, checkable results in several
  reports (`retro-sub-s01-a9e573b4.md`, `retro-sub-s02-a9445849.md`).
- Explicit worktree paths, forbidden actions, and per-AC checklists improved the briefs;
  the gap is that they were not consistently enforced or bound to the executing session.

## Proposed documentation changes (not applied)

These findings concern workflow, not the product domain. The right home for the durable
rules is `AGENTS.md` / `docs/agents/`; do not put pipeline policy into domain definitions or
architecture decisions merely to make the change durable.

### `CONTEXT.md`

**No change proposed.** The repeated evidence is about agent execution, task artifacts, and
verification provenance. It does not establish a new or changed domain term in `CONTEXT.md`.

### `docs/adr/*`

**No ADR amendment proposed.** The reviewed transcripts do not establish a cross-session
architecture decision that should be retroactively recorded as an ADR. In particular, do
not turn transient branch, skill, worktree, or test-process failures into architecture
decisions. If an implementation finding is independently confirmed as a product-design
decision, file or amend the relevant ADR through the normal owner review instead.

### Recommended patch location for follow-up

Add a `## Pipeline` section to `AGENTS.md` or a linked `docs/agents/pipeline.md` covering:
stage order and permissions; correct `cwd` at dispatch; brief-over-skill precedence;
required preflight; the base branch; definition of done; per-AC SHA-pinned evidence; and
the rule that a guard refusal is never bypassed. Keep ticket-specific logs and decisions
under the issue or a stable ticket-scoped artifact, not a session UUID in `/private/tmp`.

## Limits

The slim files omit successful tool output and sometimes truncate handbacks. Reports
therefore distinguish confirmed evidence from inferred and unverified claims. This pass
does not re-review the 12 original root-session reports, and findings from one parent
session are not promoted to a recurring pattern on their own.
