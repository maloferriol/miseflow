# Does a Supabase backend change whether files can be canonical?

Answers ticket `../issues/02-backend-vs-files.md`. Sources were official docs, fetched 2026-10-12. Anything marked **(inference)** is my reasoning from those docs, not something the docs say.

## TL;DR

- **The client runtime decides whether you can watch and write a folder of `.cook` files, not the backend.** A desktop shell (Tauri, Electron or Node) can watch a folder and write files back. A browser-only client effectively cannot: the browser API for this is experimental and non-standard.
- **(a) Plain local SQLite keeps "files are canonical" open.** The watcher, the store and the files are all on one machine and in one process. The only conflict is between an app edit and a file edit of the same Recipe, and the app can detect it on the spot.
- **(b) Supabase hosted makes "files are canonical" impractical.** The authoritative copy lives on a remote server and the folder lives on one disk. The folder becomes an import/export mirror, and conflicts surface across the network.
- **(c) Supabase/Postgres with PowerSync or ElectricSQL is technically possible but works against "files are canonical".** Each device gets a local SQLite that a watcher can feed, but both tools make the backend the authority: PowerSync by default resolves conflicts as last write wins per field, and with ElectricSQL your own API owns writes. Files can only be a projection of server state. Conflicts become three-way: file vs local DB vs server.

**What this means (inference):** "files are canonical" needs a desktop client whichever backend you pick. A pure hosted web app (which is the natural shape for (b)) cannot do it reliably. Whichever watcher you use, it has to cope with missing filenames and atomic-replace saves, so plan to re-scan the directory and compare content hashes rather than trust individual events. Ticket 05 covers this in detail.

## (a) Plain local SQLite in a desktop/local app

- **Detect file changes and push them in:** Yes. The watcher (Tauri or Node) and the SQLite database run in the same process on the same disk. A changed `.cook` file can be parsed and upserted into the database inside one local transaction.
- **Write files back:** Yes, through the same fs APIs. The app has to ignore the watch events its own writes trigger, for example by remembering the hash of what it just wrote. **(inference)**
- **Where conflicts surface:** Only on this machine, when the same Recipe is edited in the app and changed on disk before the app has synced the two. Comparing a stored hash or mtime against the file detects it, and the app can show it immediately. No network is involved.
- **Fit with "files are canonical":** Kept open. SQLite's own docs endorse it as the on-disk store for desktop apps (https://www.sqlite.org/whentouse.html), and nothing stops the database from being a rebuildable index or cache of the folder. One caveat from the same page: don't put the `.db` file itself in a network-synced folder, because "file locking logic is buggy in many network filesystem implementations". The `.cook` folder can live in Dropbox or iCloud. The database should stay local. **(inference from the SQLite page)**
- **Portability/exit:** Best of the three. The exit artifact is the folder itself.

## (b) Supabase hosted

- **Detect file changes and push them in:** Only if a desktop client exists to run the watcher. The watcher then has to call the Supabase API over the network. A Supabase-hosted web client cannot see the user's folder in any reliable way (see the browser row above), and server-side code (Edge Functions, Postgres) cannot reach the user's disk at all. **(inference)**
- **Write files back:** Again, only through a desktop client. That client would subscribe to changes, for example with Realtime `postgres_changes` (https://supabase.com/docs/guides/realtime/postgres-changes), and write files. The Realtime page does not document delivery guarantees or replay after a disconnect. A desktop mirror would therefore need its own catch-up query on reconnect. **(inference)**
- **Where conflicts surface:** Between the local folder and the remote rows, discovered only when the client is online. If more than one device or person is involved, each device's folder is a separate copy, and the server is the only shared meeting point.
- **Fit with "files are canonical":** Impractical. The thing every client can reach is the server, so the server is canonical by construction. A folder on one person's disk cannot be canonical for everyone else. The folder degrades to an import/export or mirror. **(inference)**
- **Self-hosting as an exit:** Supabase's local stack "runs in Docker containers" and is presented as a dev tool ("build and test locally, then connect your project to a hosted one"), not as something an end user runs on a desktop (https://supabase.com/docs/guides/local-development/cli/getting-started). Exit would be a Postgres dump or a `.cook` export, not "the files are already there".

## (c) Supabase/Postgres plus a local-first sync layer

### PowerSync

- **Architecture:** "App clients always read data from the client-side SQLite database." Local writes apply immediately and are queued in `ps_crud`. The `uploadData()` function, which you implement, sends them to your backend API, and the backend writes to Postgres (https://docs.powersync.com/architecture/client-architecture). With Supabase, the upload goes through the Supabase client library (https://docs.powersync.com/integration-guides/supabase-+-powersync).
- **Detect file changes and push them in:** Yes, and it works offline. The watcher writes to the local PowerSync SQLite, and the queue uploads later. Client SDKs exist for Node.js, Web and others. Tauri is **alpha**, and Electron is mentioned only for native build notes (https://docs.powersync.com/client-sdks/overview, https://docs.powersync.com/client-sdks/reference/node).
- **Write files back:** Yes. Downstream changes land in the local SQLite, and the app writes them out to `.cook` files.
- **Where conflicts surface:** On the server, after the fact. "It is up to your app backend to implement these operations and associated conflict handling". With a simple backend the result is "per-field Last-Write-Wins", and deletes win over updates (https://docs.powersync.com/usage/lifecycle-maintenance/handling-update-conflicts). There are also two local hops (file vs local DB, then local DB vs server), which makes the conflict three-way.
- **Fit with "files are canonical":** Fights the model. The server decides the winner, then overwrites the local DB, which in turn overwrites the file. In the same way, a hand-edit to a file can silently lose to a concurrent edit from another device. Field-level LWW also doesn't map well onto one `.cook` text blob: either the whole file is one field, which means coarse LWW, or the file is parsed into fields and then serialised back, which loses the user's formatting. **(inference)** Files can be a synced projection, not the canonical store.

### ElectricSQL

- **Architecture:** "Electric does not do write-path sync." It syncs reads from Postgres. Writes go through your own API, using one of four patterns: online writes, optimistic state, shared persistent optimistic state, or through-the-DB sync with PGlite (https://electric.ax/docs/guides/writes).
- **Detect file changes and push them in:** Yes, but your own code calls your own write API, and offline needs pattern 3 or 4.
- **Write files back:** Yes, from the synced read stream.
- **Where conflicts surface:** You build the handling yourself. The server API accepts or rejects a write. The client rebases or rolls back, and the guide's baseline rollback is to "clear all local state".
- **Fit with "files are canonical":** Same as PowerSync. Postgres is the authority, and the files are downstream of it.

## Verdict for the ticket

| Option                   | Watch and push in                  | Write back                 | Conflicts surface                                | "Files canonical"                                           |
| ------------------------ | ---------------------------------- | -------------------------- | ------------------------------------------------ | ----------------------------------------------------------- |
| (a) Local SQLite         | Yes (same process)                 | Yes                        | Locally and immediately (app vs file)            | **Open**. The DB can be a derived index                     |
| (b) Supabase hosted      | Only with a desktop client, online | Only with a desktop client | Remote, on reconnect, across devices             | **Impractical**. The server is canonical                    |
| (c) PowerSync / Electric | Yes, into local SQLite, offline    | Yes                        | Server-authoritative (LWW by default), three-way | **Impractical as canonical**. Possible only as a projection |

If portability/exit is the top driver and the files are meant to be canonical, the evidence favours (a). If Supabase is adopted later for multi-device use, the rule the docs imply is that the folder becomes an export/mirror rather than the source of truth. **(inference)**
